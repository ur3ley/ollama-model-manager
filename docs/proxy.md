# Встроенный auth-прокси

Документ описывает целевую архитектуру: менеджер сам проксирует Ollama, проверяет
API-токены и работает как демон с трей-иконкой. Контейнер `ollama-auth` (nginx +
podman) больше не нужен; его конфиг и юниты сохранены в `legacy/` для отката.

## Зачем

Сейчас токены выпускает `TokenManager` (KDE Wallet, папка `ollama-auth`), но проверяет
их nginx в контейнере. Цепочка «KWallet → Python → tmpfs-сниппет → `podman exec nginx
-s reload`» хрупкая и оставляет токены в открытом виде в tmpfs. Встроенный прокси
убирает посредников: токены читаются из кошелька в память процесса, наружу не пишутся,
выпуск и отзыв действуют на следующем же запросе.

## Топология

```
клиент (LAN / интернет)
  → [TLS на роутере, 443]                ← не меняем
  → 192.0.2.10:11434 (прокси менеджера)
  → 127.0.0.1:11434 (Ollama)
```

Локальные клиенты (`ollama` CLI, сам менеджер) ходят на `127.0.0.1:11434` напрямую,
без токена. Прокси слушает только внешние адреса.

## Режимы прослушивания

| Режим | Адрес | Порт |
|---|---|---|
| Выбранные интерфейсы | конкретные IPv4/IPv6-адреса из списка | может совпадать с портом Ollama (`11434`) |
| Все интерфейсы | `0.0.0.0` / `::` | обязан отличаться от порта Ollama (по умолчанию `11435`) |

Причина: Linux не позволяет занять `0.0.0.0:P`, если тот же `P` уже слушает
`127.0.0.1` (проверено). Адрес `192.0.2.10:P` рядом с `127.0.0.1:P` — можно.

Валидация при применении настроек — реальная попытка `bind()` на каждый адрес, а не
только сравнение чисел. Если занято — показать адрес и, по возможности, процесс.

## Компоненты

- `src/proxysettings.{h,cpp}` — `ProxyConfig` (адреса, порт, апстрим, лимиты),
  загрузка/сохранение в `QSettings` (`~/.config/ollama-manager/config.ini`),
  разбор `--listen`/`--upstream`, планирование адресов по `QNetworkInterface`.
- `src/tokenmap.{h,cpp}` — карта «SHA-256(token) → device»; строится из
  `TokenManager::entries()`. В памяти нет открытых токенов.
- `src/ollamaproxy.{h,cpp}` — `QTcpServer` + минимальный HTTP/1.1-парсер и
  прозрачный релей к апстриму.
- Диалог настроек: вкладка «Прокси» (режим, список адресов, порт, апстрим, статус).
- Трей: показать окно, API-токены, статус прокси, выход. Один процесс, single-instance
  через `QLocalServer`; повторный запуск поднимает окно уже работающего экземпляра.
- `--daemon` — без окна; `--no-tray` — без трея (для юнита без графической сессии).

## Поведение прокси

1. Принять соединение, прочитать заголовки до `\r\n\r\n` (лимит 32 КиБ, не более 100
   заголовков; URI ≤ 8192 байт, метод ≤ 32 байт) → `431`/`414`/`400`. Таймаут на
   получение заголовков — 10 с, он не зависит от `idleTimeout`.
2. Проверить токен:
   - `Authorization: Bearer <token>` (схема без учёта регистра) или `X-Api-Key: <token>`;
   - сравнение через SHA-256 + `QHash` (не побайтовое сравнение, без утечки по времени);
   - нет токена/неверный → `401` JSON `{"error":"unauthorized"}`, закрыть.
3. Проверить `Content-Length`: только `^\d{1,19}$`; дубликат (даже одинаковый) → `400`;
   `Transfer-Encoding` одновременно с `Content-Length` → `400`; больше лимита → `413`.
   Тело считается по **фактически переданным** байтам, поэтому chunked и «врущий»
   `Content-Length` тоже упираются в лимит.
4. Соединиться с апстримом (таймаут 10 с → `502`).
5. Переписать заголовки и отправить:
   - `Host: 127.0.0.1:<upstream-port>` (Ollama 0.40 отклоняет чужой Host);
   - `X-Ollama-Device: <device>` (клиентский заголовок с таким именем отбрасывается;
     имя устройства обязано матчить `^[A-Za-z0-9._-]{1,32}$`, иначе запись из кошелька
     игнорируется);
   - `Connection: close` (keep-alive не поддерживаем — после ответа закрываем);
   - hop-by-hop заголовки (`Connection` и перечисленные в нём, `TE`, `Trailer`, `Upgrade`,
     `Proxy-Authorization`, `Proxy-Authenticate`, `Keep-Alive`) не пересылаются;
     `Transfer-Encoding` пересылается — тело идёт как есть;
   - управляющие символы (`NUL`, `CR`, байты < 0x20 кроме `\t`, 0x7f+) в request-line,
     именах и значениях → `400`; obs-fold и пустые имена → `400`;
   - остальные заголовки и тело — байт-в-байт.
6. Дальше — прозрачный релей в обе стороны без буферизации: NDJSON `/api/chat`,
   SSE `/v1/chat/completions` и chunked-запросы должны идти потоком. Backpressure:
   при 4 МиБ непрочитанных данных чтение противоположной стороны приостанавливается
   и возобновляется ниже 1 МиБ.
7. Таймауты: простой в релее 3600 с (сброс на любой активности), отсутствие данных от
   апстрима 300 с, прогресс записи в апстрим контролируется по `bytesWritten`.
8. Логи: адрес, device, метод, путь (обрезанный и очищенный от управляющих символов),
   статус, байты. Значения токенов и заголовки авторизации не логируются.

## TLS между OPNsense и прокси

Внешний TLS по-прежнему терминируется на OPNsense. Второе плечо (OPNsense → хост)
можно тоже зашифровать; поддерживаются три режима, по умолчанию — свой мини-CA.

### Режим `internal` (по умолчанию)

- **Root CA** `Ollama Manager Internal CA`, срок 10 лет, генерируется один раз:
  `~/.config/ollama-manager/tls/ca.crt` (публичный) и `ca.key` (0600).
- **Листовой сертификат** на 90 дней, SAN `IP:192.0.2.10` и
  `DNS:ollama.example.org`, подписывается CA. Продление — за 30 дней до
  истечения, ежедневная проверка по таймеру, hot-reload слушателя.
- В OPNsense импортируется **только CA** (один раз): upstream TLS on,
  «TLS: Trusted Certificate» = `ca.crt`, «Servername override» =
  `ollama.example.org`, «Verify Certificate» включена. Повторных импортов
  при продлении листа нет.
- Кнопка «Экспортировать CA…» в настройках прокси отдаёт `ca.crt` для импорта.

Почему не публичный CA: апстрим адресуется по IP, а публичные CA не выдают
сертификаты на приватные адреса; плюс LE потребовал бы DNS-01 через deSEC, токен
и продление каждые 60 дней. Пиннинг собственного CA для внутреннего плеча строже
и проще в эксплуатации.

### Режим `files`

Пользователь сам указывает `cert`/`key` (например, выданные внутренним PKI
организации). Менеджер следит за mtime, перечитывает файлы и показывает срок
действия. Проверка цепочки — на стороне OPNsense.

### Режим `letsencrypt` (опция)

Публично доверенный сертификат через Let's Encrypt и DNS-01 у deSEC (dedyn.io):

- токен deSEC со scope только на `_acme-challenge.<домен>` и сроком 4 месяца
  хранится в KWallet (папка `ollama-auth`, ключ `tls:desec-token`);
- менеджер по таймеру запускает `lego --dns desec --domains ollama.example.org
  --path ~/.config/ollama-manager/tls/le` (внешняя зависимость: `lego` в PATH),
  перечитывает `certificates/*.crt|.key` и делает hot-reload;
- продление — за 30 дней, при ошибке статус в трее и в диалоге, повтор через сутки.

Сам ACME в C++ не реализуется: JWS, криптография и поллинг DNS — слишком большой
и рискованный объём для этой задачи.

### Хранение и ротация

Каталог `~/.config/ollama-manager/tls/` — 0700, ключи 0600, без пароля (нужен
автоматический перезапуск без участия пользователя). Защита — права доступа и
шифрование диска; CA-ключ используется только для подписи листов.



## Безопасность

- Токены на диске не появляются вообще (в отличие от старого `maps.conf`).
- В памяти — только SHA-256, так что дамп процесса не раскрывает токены. Сравнение
  идёт по хешу: timing-атака «посимвольно» невозможна, восстановить токен по времени
  отклика нельзя (нужен прообраз SHA-256). Это осознанное решение.
- `X-Ollama-Device` от клиента игнорируется (нельзя выдать себя за другое устройство);
  имена устройств из кошелька валидируются по `^[A-Za-z0-9._-]{1,32}$`.
- Ограничения: 100 МиБ на тело (по факту переданных байт), 32 КиБ на заголовки,
  100 заголовков, 256 соединений по умолчанию (`0` — полный отказ), таймауты
  заголовков/апстрима.
- Логи очищаются от управляющих символов; токены и `Authorization` не логируются.
- Цепочка: внешний TLS на OPNsense, внутренний — свой CA (см. выше).
- Клиентские сертификаты (mTLS) не используются: авторизация — токеном; проверка
  сертификата прокси выполняется на стороне OPNsense.

## Конфигурация

`~/.config/ollama-manager/config.ini`, группа `[proxy]`:

```ini
[proxy]
enabled=true
mode=interfaces          ; interfaces | all
interfaces=eno1/192.0.2.10
port=11434
upstream=127.0.0.1:11434
maxConnections=256
tls=internal             ; off | internal | files | letsencrypt
tls_cert=                ; для files
tls_key=                 ; для files
```

Флаги командной строки перекрывают файл:

```
ollama-model-manager --daemon --listen 192.0.2.10:11434 --upstream 127.0.0.1:11434
ollama-model-manager --daemon --listen 0.0.0.0:11435
ollama-model-manager --show          # поднять окно работающего экземпляра
```

## systemd

Готовый юнит лежит в `packaging/systemd/ollama-manager.service` (устанавливается в
`share/ollama-manager/systemd`). Он headless (`--no-tray`) и с hardening:

```ini
[Service]
ExecStart=/usr/bin/env ollama-model-manager --no-tray
Restart=on-failure
UMask=0077
LimitCORE=0
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=read-only
ReadWritePaths=%h/.config
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK
```

Установка:

```bash
systemctl --user link /usr/local/share/ollama-manager/systemd/ollama-manager.service
systemctl --user daemon-reload
systemctl --user enable --now ollama-manager.service
```

Если нужна трей-иконка, запускай `ollama-model-manager --daemon` из автозапуска
графической сессии (`.desktop` в `~/.config/autostart`), а headless-юнит не включай:
single-instance не даст запуститься двум экземплярам.

Старые `ollama-auth.service` и `ollama-auth-tokens.{service,timer}` отключаются.

## Тесты

`build/proxy-selftest` — 35 проверок, без сети и без Ollama: поднимает фейковый апстрим на
`QTcpServer`, проверяет авторизацию, переписывание заголовков, стриминг, chunked-тела,
лимиты и таймауты, отбраковку мусора, TLS-handshake/стриминг с собственным CA, бюджет
соединений до и после handshake, symlink-политику. Отдельно — фаззинг парсера
(`tests/audit/fuzz-head.cpp`, libFuzzer + ASan/UBSan) и стресс жизненного цикла
(`tests/audit/tls-stress.cpp`).

Ключевые сценарии:

1. без токена → `401`;
2. неверный токен → `401`;
3. `Bearer` → `200`, апстрим увидел `Host: 127.0.0.1:<port>` и `X-Ollama-Device`;
4. `X-Api-Key` → `200`;
5. стриминг: клиент получает первый чанк до завершения ответа апстрима;
6. chunked-тело запроса доходит байт-в-байт;
7. заголовки > 32 КиБ → `431`;
8. клиентский `X-Ollama-Device` не подменяет device из токена;
9. bind на конкретный адрес при занятом `127.0.0.1:порт` (эмуляция Ollama).

## Миграция

1. Собрать новую версию, запустить вручную на свободном порту (`11436`), прогнать curl.
2. Остановить старую схему: `systemctl --user disable --now ollama-auth.service
   ollama-auth-tokens.timer ollama-auth-tokens.service`.
3. Включить новую на `192.0.2.10:11434` (TLS `internal`).
4. Импортировать `~/.config/ollama-manager/tls/ca.crt` в OPNsense (Trusted Certificate),
   у upstream `ollama` включить TLS (Verify Certificate on, Servername override
   `ollama.example.org`), reload nginx. Проброс остаётся `443 → 192.0.2.10:11434`.
5. Контейнер `ollama-auth` не удалять, пока не пройдёт неделя эксплуатации.

Откат — см. `legacy/README.md`.
